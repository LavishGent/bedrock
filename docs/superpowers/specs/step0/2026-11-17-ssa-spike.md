# Step 0 spike: SSA, CHA and VTA over the full analysis universe

**Date:** 2026-11-17
**Plan:** `../2026-11-17-bedrock-poc-plan.md`, step 0 (section 8), decision 4, section 7
**Raw result:** `ssa-spike-result.json` (written by the command below)

## What was run

- **Target**: `spike/target`, its own module `example.com/spike`. It has a repo package (`internal/repo`, one `(*sql.DB).ExecContext` call), a handler (`internal/handler.(*Items).Create`), and `cmd/server` registering one chi route, `r.Post("/items", h.Create)`. The target depends on `github.com/go-chi/chi/v5 v5.5.0`.
- **Program**: `spike/ssaspike` in the root module. It runs these phases: `packages.Load` (`LoadAllSyntax`, tests excluded), `ssautil.AllPackages` with `ssa.InstantiateGenerics`, `prog.Build()`, universe `ssautil.AllFunctions(prog)`, `cha.CallGraph(prog)`, and `vta.CallGraph(universe, cha)`. It then classifies every non-builtin call site in the universe.
- **Toolchain**: Go `go1.26.11`, `golang.org/x/tools v0.52.0`, pinned in the plan (section 7, "Pinned toolchain and build profile").
- **Build profile**: `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`, no build tags, `GOFLAGS=-mod=readonly GOWORK=off GOTOOLCHAIN=local`. The profile is cross-compiled from the host, so the result does not depend on the developer machine's OS.
- **Bounds**: `-timeout 120s -mem-limit-mib 4096`. A watchdog samples `runtime/metrics` (`/memory/classes/total:bytes`) every 25 ms. It aborts with exit 3 and a partial result (`status: timeout | memory_limit`, `aborted_in_phase`) when either limit is crossed. `debug.SetMemoryLimit` is set to the same value as a soft GC target. Both aborts were exercised:

  | Run | Result |
  | --- | --- |
  | `-mem-limit-mib 300` | `memory_limit`, exit 3, aborted in `load` (305 MiB) |
  | `-timeout 600ms` | `timeout`, exit 3, aborted in `vta` |

- **Host**: Apple M5 Pro, 18 cores, 48 GiB. Warm module cache. A run with an empty `GOCACHE` took the same time (1.04s), because `go list` does not compile anything for this load mode.

Reproduce from the repo root:

```sh
go build -o /tmp/ssaspike ./spike/ssaspike
/tmp/ssaspike -dir spike/target -timeout 120s -mem-limit-mib 4096 \
  -out docs/superpowers/specs/step0/ssa-spike-result.json \
  -diag-out /tmp/spike-diags.jsonl -dump-module-sites /tmp/spike-sites.jsonl
```

## Symbol ID collisions

Of the 16,966 universe functions, 69 groups share a go/ssa `String()`:

- **57 equivalent groups** (same signature and same VTA targets): 38 instance and 19 wrapper groups, for example `(*database/sql.driverConn).releaseConn$bound` with 7 copies.
- **11 `instance`/`method` groups that differ**: instances whose type arguments are still type parameters print the same as the generic origin, for example `(*unique.canonMap[T]).Load`.
- **1 wrapper group that differs**: `(net/http.Handler).ServeHTTP$bound` has 5 copies with different VTA targets.

The schema's canonicalization rules C1–C3 (`../schema/README.md`) are the response. Collision grouping was non-deterministic in the first spike version because go/ssa builds packages in parallel; it was fixed by sorting. This is why IDs must never depend on creation order.

## Open issues for the coordinator (not changed in the plan)

These follow from the measurements. None changes the plan's decisions here; each needs an owner decision.

1. **Plan section 7's relevance rule makes the clean demo indeterminate.** Section 7 says any unknown call (bodyless, `unsafe`, reflection, unresolved interface or dynamic call) reachable from a governed Entry gives `2` "unless proven irrelevant". On the clean spike, the one route handler reaches 1,844 such sites, all in the standard library. `SaveItem`, inside the approved boundary, reaches 1,841. Without a concrete "proven irrelevant" rule, `restrict_concept_to_boundary` on the clean demo will be `INDETERMINATE` (exit 2), never `PASS`. The section 10 matrix ("each rule kind passes") would then fail.

   The plan needs an explicit, sound irrelevance criterion before step 4. One direction, not adopted here: under the closed-world whole-program universe, a zero-target VTA site has no callee in the program, so the remaining risk comes only from reflection, `unsafe` and bodyless functions. A bodyless standard-library function that provably cannot call back into Go code (for example `runtime.getg`) cannot reach a bound concept. The policy must not silently exempt libraries; the criterion has to be stated and tested.

2. **Wrapper merging (C2) is imprecise but does not break the Entry caveat.** Merging the five `(net/http.Handler).ServeHTTP$bound` copies takes the union of their callers and of their VTA targets. Every target already had an incoming edge from some copy, so no symbol's zero-indegree status changes, and the Entry set is the same with or without the merge. The merge only adds paths (caller of copy 1 → target of copy 2). With Entry fixed, extra paths can only turn a `reachable_from` pass into a fail, never a fail into a pass. So C2 is conservative, unlike the spurious-edge case in the decision 4 caveat. Cost: possible false violations through `http.Handler` method values. Alternative if that bites: key `$bound` wrappers by their creation site.

3. **The library Entry population is large.** 4,566 standard-library and 29 chi functions are `Entry` under the "no incoming edges" definition, and they reach the module's handler and repository code through `net/http` and chi dispatch. For the spike this is harmless: `SaveItem` is inside the boundary, and the path into it passes through the handler. But any module helper reachable from library dispatch without passing through `B` will fail `reachable_from`, even if module code reaches it only through `B`. That is conservative and matches the parent spec, but expect it when debugging step 4 fixtures. The `Entry` decision is unchanged.

4. **`x/tools` choice.** `v0.53.0` was released on 2026-11-17, the day of this spike. `v0.52.0` is pinned instead, so the pin is not a same-day release. Both require `go 1.26.0`.
